## 代码链路

1. `RomeBookingPriorityService` 从内存中的官方证据目录计算规则，不请求 AI、Viator、Google Places 或业务数据库。
2. 但它与整个 Spring Boot 应用共用启动生命周期，仍需等数据库连接、Flyway、JPA 等初始化完成。
3. priority 的前端超时为 120 秒，地点和票务请求默认超时为 12 秒。没有任何结果时，页面等全部请求结束才展示静态景点兜底列表，因而可能一直等待 priority。
4. 三个结果查询均明确配置 `retry: false`，全局还关闭了窗口重新聚焦时刷新。失败后没有针对服务唤醒的自动重试，需手动重试等后续动作。
5. 超时、连接失败、非成功状态和非 JSON 返回都会进入 priority 不可用状态。不同 HTTP 状态目前使用相同文案，无法从统一错误标题确定具体原因。
6. `fetchWithTimeout` 的计时器在 fetch 收到响应头后清除，未覆盖后续 JSON 响应体读取。这是额外的超时边界缺口，本次没有证据证明它触发了当前事故。

## 建议修复顺序

1. 如果要求任意时间首次打开都快速响应，采用不会空闲休眠的后端实例。需要用户确认费用和实例选择，本次没有执行升级。单纯继续延长前端超时不能实现此目标。
2. 前端立即呈现景点骨架，并区分“正在连接/唤醒服务”和最终失败；为暂时性连接、超时及可重试服务端错误增加有总时限的退避恢复。避免无限重试、对 4xx 无条件重试或用票务数据推测 priority。
3. 对响应状态、耗时和失败阶段保留可诊断信息；让超时覆盖响应体读取。维持三类来源独立展示。
4. 分别验证休眠后首次访问、已就绪访问、临时 503 后恢复、持续不可达和单个 Provider 失败。后端优化需测量后再决定，不能通过关闭数据库结构检查掩盖真实启动错误。
